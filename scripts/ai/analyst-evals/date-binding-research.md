# Research: PrismaPg Date binding and Jakarta business time

## Summary / recommended decision
**No released upstream date fix was verified. Do not upgrade to 7.10.1 expecting this bug to disappear.** GitHub's official latest-release API returned 7.10.1, but its tagged adapter source retains the faulty read and write conversions. PR #29481 is open/unmerged; PR #28071 is closed/unmerged. Prefer a **temporary, explicitly verified UTC policy on every Prisma database session**, while keeping business boundaries, grouping, and display explicitly `Asia/Jakarta`. If that operational policy cannot be guaranteed, a **narrow, parameterized, typed raw-query ISO-string workaround** can protect instant inputs, but does not fix timestamptz result decoding or ORM writes. A future upgrade is preferred only after a fixed release is verified and regression-tested. [GitHub latest release](https://api.github.com/repos/prisma/prisma/releases/latest), [7.10.1 conversion source](https://raw.githubusercontent.com/prisma/prisma/7.10.1/packages/adapter-pg/src/conversion.ts), [29481 API](https://api.github.com/repos/prisma/prisma/pulls/29481), [28071 API](https://api.github.com/repos/prisma/prisma/pulls/28071).

Scope: read-only investigation, except this requested new research artifact. No implementation, dependency/config/schema/database/deploy changes; no `.env` access. Local diagnostics and Node version below are supplied task evidence, not independently rerun here. Upstream status is a point-in-time API observation, not a prediction.

## Findings

1. **Claim: the local 7.10.0 adapter strips timezone information before PostgreSQL receives Date parameters.** **Support: direct local source evidence; high confidence.** `node_modules/@prisma/adapter-pg/package.json` reports 7.10.0. In `dist/index.js`, `performIO` maps arguments using `mapArg` before calling `client.query` (approximately lines 678–693). `mapArg` converts strings tagged `scalarType === 'datetime'` to Date, recursively maps list arguments, and formats Date using UTC components. Except `DATE`, `TIME`, and `TIMETZ`, it uses `formatDateTime`, which emits `YYYY-MM-DD HH:mm:ss[.SSS]` **without Z/offset** (approximately lines 365–415). Thus merely using an ISO-looking datetime input is not sufficient if Prisma still tags that parameter as datetime. The same logic is present in [official 7.10.1 source](https://raw.githubusercontent.com/prisma/prisma/7.10.1/packages/adapter-pg/src/conversion.ts). Local schema begins with `@db.Timestamptz(6)` fields (`prisma/schema.prisma`, User.createdAt/updatedAt/deletedAt); no type migration is called for by this evidence.

2. **Claim: this is instant transport corruption, not a reason to abandon Jakarta business time.** **Support: direct PostgreSQL documentation plus interpretation; high confidence.** PostgreSQL interprets offset-free timestamptz input in the session `TimeZone`, converts it to UTC, and renders timestamptz results in session timezone. Explicit offsets identify an instant independently of session timezone. Therefore the adapter's UTC wall-clock text becomes a different instant under non-UTC sessions. [PostgreSQL date/time types, §8.5.1.3](https://www.postgresql.org/docs/current/datatype-datetime.html#DATATYPE-DATETIME-INPUT-TIMESTAMPS).

   Supplied bounded diagnostic evidence: intended epoch `1790812800000`; raw bound Date shifts **+4h in America/New_York**, **−7h in Asia/Jakarta**, and is correct in UTC; offset-aware ISO binding preserves epoch. This agrees with the documented interpretation and inspected conversion. These values were not rerun by this researcher. Node `22.23.5` is task-provided context, not an independently established cause. Evaluate correctness with server-side `extract(epoch from ...)*1000` or equivalent numeric output, not Date readback alone, because the separate read defect can mask a bad write. [PostgreSQL epoch/date functions](https://www.postgresql.org/docs/current/functions-datetime.html).

3. **Claim: reads are independently broken; fixing input alone is incomplete.** **Support: direct source; high confidence.** Local `normalize_timestamptz` replaces the returned offset with `+00:00` without adjusting the wall clock. The parser applies to both scalar timestamptz and timestamptz arrays. `performIO` installs adapter-specific parsers per query, so a broad `pg.types` global parser override is not a reliable remedy for those OIDs. Example interpretation: actual `09:00+07` becomes `09:00Z`, seven hours late. A write −7h error and read +7h error can accidentally cancel in a round-trip assertion. [7.10.1 conversion source](https://raw.githubusercontent.com/prisma/prisma/7.10.1/packages/adapter-pg/src/conversion.ts), [proposed correction commit](https://github.com/prisma/prisma/commit/d0af4bd71475fc55798b26fccdcca657db21c0cb), [issue 26786](https://github.com/prisma/prisma/issues/26786), [write-focused issue 28629](https://github.com/prisma/prisma/issues/28629). Issue #23606 describes related raw timestamp lookup behavior, but its closed status does not establish resolution of these adapter paths. [23606](https://github.com/prisma/prisma/issues/23606).

5. **Claim: session UTC and Jakarta business days are compatible.** **Support: direct PostgreSQL semantics; recommendation is inference; high confidence.** A UTC session prevents both inspected adapter paths from applying a nonzero offset incorrectly. It does not change the business definition of a day. Group a timestamptz with `(event_time AT TIME ZONE 'Asia/Jakarta')::date` or an explicitly zoned `date_trunc`, and convert Jakarta start/end civil boundaries into instants before `[start,end)` filtering. Render UI dates in Asia/Jakarta, not implicitly in session/OS timezone. A Jakarta midnight corresponds to 17:00 UTC on the preceding UTC date; UTC midnight bucketing is therefore not equivalent. [PostgreSQL AT TIME ZONE/date_trunc](https://www.postgresql.org/docs/current/functions-datetime.html).

   Session UTC must cover **every physical pooled/reconnected connection** and any transaction that changes timezone; setting Node `TZ`, setting one arbitrary pooled connection, or merely observing a database default is insufficient proof. `SET LOCAL` is transaction-scoped, while ordinary `SET` is session-scoped; test checkout/reconnect behavior and transaction restoration. This is a future policy recommendation only, not a configuration change performed here. [PostgreSQL SET](https://www.postgresql.org/docs/current/sql-set.html).

6. **Claim: narrowly typed raw ISO-string parameters are a viable temporary input workaround, but not a universal Date replacement.** **Support: local conversion and supplied diagnostic plus PostgreSQL semantics; medium confidence outside tested shapes.** For SQL explicitly expecting an instant, a bound plain string `date.toISOString()` with explicit `::timestamptz` can retain the offset if Prisma classifies it as string rather than datetime. Preserve parameterization; never concatenate values into SQL. The supplied diagnostics support this path. node-postgres documents string pass-through, Date conversion, and recursive array conversion, but Prisma's earlier mapping is the decisive extra layer here. [node-postgres queries](https://node-postgres.com/features/queries), [node-postgres types](https://node-postgres.com/features/types), [Prisma mapping](https://raw.githubusercontent.com/prisma/prisma/7.10.1/packages/adapter-pg/src/conversion.ts).

   Caveats: apply only where SQL target semantics are explicitly timestamptz; timestamp-without-time-zone ignores timezone indications and has different wall-clock semantics. Do not globally rewrite Date values in timestamp/date/time columns, JSON, or ORM operations. Date arrays need a separate tested `timestamptz[]` binding strategy; adapter recursion and Prisma metadata can reconvert elements. Reject invalid/nonfinite Date before serialization; explicitly preserve null behavior. JavaScript Date millisecond precision cannot represent all PostgreSQL `TIMESTAMPTZ(6)` microseconds. This workaround protects inputs only; outputs still require UTC session or an independently tested representation such as numeric epoch/text. [PostgreSQL type precision and timestamp input semantics](https://www.postgresql.org/docs/current/datatype-datetime.html), [node-postgres precision caveat](https://node-postgres.com/features/types).

## Option comparison (researcher recommendation)

| Option | Benefit | Main limitation | Recommendation |
|---|---|---|---|
| Upgrade to **verified** fixed release | Central upstream read/write remedy | No fixed release verified; 7.10.1 retains code | Preferred long-term, gated on tagged source and tests |
| UTC policy for every Prisma session + explicit Jakarta business SQL/UI | Covers inspected input and result bugs without changing business timezone | Pool enforcement and other timezone-dependent SQL must be audited | Safest temporary systemic policy if approved |
| Narrow raw ISO string + explicit timestamptz cast | Small, locally proven instant input surface | Does not fix reads/ORM writes; typed parameters/arrays need tests | Targeted fallback or defense, not general fix |
| Broad driver/adapter patch | Could correct both paths centrally | Custom maintenance, timestamp-vs-timestamptz distinctions, arrays, precision, and adapter parser overrides | Avoid as first choice; only with dedicated audit/test ownership |

Comparison derives from findings 1–6 and their primary sources, not a measured production rollout.

## Regression matrix before any approved implementation

Run **process TZ independently** from database session TimeZone: UTC / Asia/Jakarta / America/New_York. At minimum test all session zones under UTC process, then cross-check non-UTC process zones. Include NY winter and summer to detect DST assumptions. [PostgreSQL timezone semantics](https://www.postgresql.org/docs/current/datatype-datetime.html), [node-postgres local timestamp behavior](https://node-postgres.com/features/types).

- Inputs: raw bound Date, bound ISO string explicitly cast timestamptz, ORM create/update/filter; timestamp-without-zone control; null and rejected invalid Date; list/array parameters separately.
- Independent storage assertions: numeric database epoch equals intended epoch on insert/update/filter; never rely solely on adapter Date round-trip.
- Reads: preseed known-correct timestamptz independently, then assert scalar and array Date epochs; include nonzero milliseconds and an independently stored microsecond fixture to document precision loss.
- Business boundaries: just before/at/after Jakarta midnight; `[start,end)` excludes next day's midnight; explicit Jakarta grouping agrees with UI under every session timezone. UTC grouping must intentionally differ around 17:00Z.
- Pooling: concurrent sessions, reconnect, transaction-local changes/restoration; verify session policy on actual query connections, not a single bootstrap `SHOW`.
- Fixture qualification: qualify schema/table or explicitly establish intended `search_path`. The supplied fixture search_path failure is separate from Date transport and must not be counted as either a timezone regression or a pass. [PostgreSQL schemas/search_path](https://www.postgresql.org/docs/current/ddl-schemas.html).

This is a proposed matrix, not tests executed in this research-only run.

## Contradictions / validation limits
- Search/PR language says “fixes,” but API merger fields show neither cited PR merged; tagged 7.10.1 source still contains both defects. PR prose/commit availability is proposal evidence, not shipping evidence.
- node-postgres's general Date serialization documentation does not establish PrismaPg behavior: Prisma transforms parameters and supplies custom result parsers before/around node-postgres.
- `source_check` was called for release/fix status and PostgreSQL instant/grouping claims. It returned passages with semantic assessment unavailable (`unclear`); those results were not treated as validation. Original GitHub API, tagged source, and PostgreSQL documentation were manually inspected instead.
